# 铁律规则 (所有子skill必须遵守)

## 铁律 0: 代码即事实

所有写入知识库文档的内容必须来源于实际源码。禁止凭 AI 训练数据中的通用 NestJS 知识编造项目特有的实现细节。

---

## 铁律 1: 装饰器和参数必须解析到实际值

NestJS 大量使用装饰器元数据。遇到以下情况必须解析到具体值：
- `@Get(':id')` → 必须写出实际路径模板 `/api/users/:id`
- `@UseGuards(JwtAuthGuard)` → 必须写明守卫名称和路径
- `@Throttle(10, 60)` → 必须写明速率限制次数和窗口
- `@ApiProperty({ example: 'test@example.com' })` → 必须提取 example 值

**禁止行为**：只写"使用了装饰器"而不给出具体参数。

---

## 铁律 2: 技术栈版本必须尽可能精确

按以下优先级确认：
1. 查 `package.json` 中的 dependencies
2. 查 `nest --version` 或 `@nestjs/core` 版本
3. 查看 `tsconfig.json` 的编译配置

**输出要求**：
- NestJS 版本：精确到 minor（如 10.3.x）
- TypeScript 版本：精确到 minor
- 数据库 ORM：精确到类型（TypeORM 0.3.x / Prisma 5.x / MikroORM 6.x）

---

## 铁律 3: "为什么"比"是什么"更重要

每个功能模块必须回答：
- **为什么这样分层？**（如：为什么 AuthModule 独立而不是放在 UserModule？）
- **为什么选这个库？**（如：为什么用 Passport 而不是自定义认证？）
- **为什么这个路由设计成这样？**（如：为什么用 PATCH 而不是 PUT？）

---

## 铁律 4: 依赖注入关系必须完整绘制

NestJS 的核心是依赖注入。在任何模块/服务分析中：
- 必须列出 Provider 的 provide 和 useClass/useFactory
- 必须追踪 @Inject() 自定义 provider 的注入链
- 必须绘制 Module 的 imports/exports 依赖图

---

禁止自行更改文档名称、编号，禁止拆分或合并文档。

---

## 铁律 6: 验证阶段不可跳过

所有12个文档生成完毕后，必须执行 `13_verification.md` 验证流程。
验证未通过的项目不得进入交付阶段。

---

## 铁律 7: 不确定的结论必须标注

如果某个结论是 AI 从代码模式推断的（而非源码直接指明），必须在结论旁标注：
- ⚠️ **AI推断**：根据代码模式推断，建议人工确认
- ⚠️ **来源存疑**：该信息未找到源码证据

---

## 铁律 8: 子skill必须直接读源码

`_analysis/` 文件是导航索引，不是数据来源。
子skill使用 `_analysis/` 的唯一目的：找到需要读的源文件名和行号。
所有写入文档的数值、参数、代码逻辑，必须来自 `_snapshot/sources/` 的源文件。

**禁止行为**：
- 看到 `_analysis/` 有数值就直接复制进文档（必须去源码验证）
- 看到 `_analysis/` 有内容就认为已完整（必须去源码确认是否有遗漏）

### 铁律 8 补充：源码阅读策略（三档）

| 策略 | 名称 | 使用场景 |
|------|------|---------|
| **策略A** | 导航定点读 | `_analysis/` 已精确定位，信息集中 |
| **策略B** | 全文通读 | 需要理解完整逻辑流的文件 |
| **策略C** | 全局搜索读 | 信息分散在多个文件中（如 DTO、装饰器） |

各子skill推荐策略：
| 子skill | 策略 | 说明 |
|---------|------|------|
| `01_doc_overview` | 策略A | 从 project_overview.md 定位 |
| `02_doc_modules` | 策略B | 每个 Module 文件必须全文读 |
| `03_doc_routes` | 策略C | 路由装饰器分散在各 Controller |
| `04_doc_services` | 策略B | 每个 Service 文件必须全文读 |
| `05_doc_models` | 策略C | DTO/Entity 定义在多个文件中 |
| `06_doc_api` | 策略C | API 信息分布在控制器和装饰器 |
| `07_doc_database` | 策略B | 需理解完整数据流转 |
| `08_doc_config` | 策略A→B | 先定位，发现关联时全文读 |
| `10_doc_semantics` | 策略B | 每个核心文件必须全文读 |

## 铁律 9: 补厚模式下不覆盖已有内容

当目标文档已存在时：
- 读取现有文档，明确记录"已有内容边界"
- 只追加缺失的章节或缺失的表格行
- 不修改、不重写现有内容（除非发现明显错误）
- 执行完成后输出"新增了什么 / 保留了什么"的操作摘要

### 铁律 9.1: 补厚前的"是否需要补"判断

1. 读取目标文档，检查是否包含子skill模板要求的全部章节
2. 如果所有章节都已存在且有实质内容 → 输出"无需补厚，该文档已完整"
3. 如果有缺失章节或空壳章节 → 只补缺失部分

### 铁律 9.2: 补厚边界声明（执行前必说）

执行补厚前必须输出以下声明：
```
[补厚模式] 目标：{文档名}
[已有内容] {概述已有章节}
[待补充] {列出要追加的内容}
[不修改] {列出不会动的内容}
```

## 铁律 10: 禁止偷懒输出（反敷衍铁律）

### 10.1 禁止行为（发现即重做）
- ❌ 禁止使用"以此类推"、"等"、"类似地"等泛指省略
- ❌ 禁止空壳章节（只有标题没有实质内容）
- ❌ 禁止复制通用 NestJS 模板描述代替实际代码分析
- ❌ 禁止用"使用了标准 NestJS 模式"一句话带过

### 10.2 最低内容标准
| 文档 | 最低要求 |
|------|---------|
| `02_模块架构.md` | 模块图 + 每个模块至少3行说明 |
| `03_路由与控制器.md` | 路由表行数 ≥ Controller 文件数 × 2 |
| `04_服务与业务逻辑.md` | 每个 Service 至少一个方法说明 |
| `05_数据模型与DTO.md` | 模型/DTO 定义表格行数 ≥ 5 |
| `06_API接口文档.md` | API 条目数 ≥ 路由总数 |
| `10_核心函数语义.md` | 函数卡片数 ≥ 核心 Service 导出方法数 |
| `11_常见问题清单.md` | Q&A 数量 = 20 |

### 10.3 自检指令（每个文档生成完毕后必须执行）
```
□ 检查：所有数据是否有源文件:行号标注
□ 检查：表格行数是否达到铁律10.2的最低标准 → 不足则补行
□ 检查：描述是否有实质内容（非泛化描述）→ 没有则重写
```
